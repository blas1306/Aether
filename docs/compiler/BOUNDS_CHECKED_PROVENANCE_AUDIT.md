# RUST-3.B2 bounds_checked provenance audit

Decision: `INITIAL_IR_BOUNDS_CHECKS_DEFINITIONALLY_ENABLED`.

All Initial IR Array/List/Vector/Matrix get and set operations definitionally
enter SSA with `bounds_checked=true`. Initial IR schema-v1 remains unchanged.
The lowering policy now identifies this as explicit synthesis, not field
preservation and not a consequence of Python dataclass defaults. Rust SSA
lowering remains out of scope.

## Meaning and provenance

`true` directs LLVM lowering to emit the collection's runtime bounds check
before calculating and using the element address. `false` directs it to omit
that runtime check; it does not mean that a check already executed. In the
production source pipeline, omission is legal only after SSA's
`ProvenBoundsCheckEliminator` proves every obligation for the exact access
`PROVEN_SAFE`. The load/store, operand evaluation, and address calculation
remain.

The frontend constructs only the eight Initial IR operation classes. Neither
their model nor Initial IR wire schema-v1 contains the bit, so frontend
construction cannot produce `false`, Initial IR cannot distinguish the two
states, and `GeneralSSABuilder` cannot receive an Initial IR requirement for
`false`. Both Python Initial IR-to-SSA implementations now pass `true`
explicitly for all eight operations.

The SSA model and required schema-v2 field admit both values. Consequently,
hand-built SSA and imported valid schema-v2 SSA may legitimately contain
`false`; this is preservation at the SSA wire boundary, independent of Initial
IR lowering. Repository-wide search found no transformation from `false` to
`true`.

## Eight-operation inventory

The path is the same for each Array/List/Vector/Matrix get/set operation:
frontend indexing/assignment lowering constructs the corresponding `IR*`
class; the Initial IR dataclass and schema-v1 omit `bounds_checked`;
`SSARenamer` (the `GeneralSSABuilder` path) synthesizes `true`; the SSA dataclass
declares the bit and schema-v2 requires and losslessly encodes it; O0/O1 do not
change it; O2's proven-bounds pass may replace it with `false`; the LLVM backend
passes the value as `check_bounds` to the appropriate Array/List/Vector/Matrix
address helper. The compatibility `SSABuilder` was clarified identically.

Only `ProvenBoundsCheckEliminator` writes the field in production. It operates
on SSA only, changes `true` to `false`, requires all exact-site proofs to be
`PROVEN_SAFE` (both row and column for Matrix), and leaves `UNKNOWN` and
`PROVEN_UNSAFE` checked. Initial IR never observes its output. SSA DTO code is
the sole serializer/deserializer; the printer and analyses only inspect it.

The deterministic 116-program denominator produced these aggregate counts:

| Array set | 11 / 11 | 11 / 0 | 11 / 0 | 11 / 0 |

| Matrix set | 1 / 1 | 1 / 0 | 1 / 0 | 0 / 1 |

No `false` occurs at construction, O0, or O1. O2 is the first source-pipeline
stage where it appears. Adversarial tests independently cover every operation,
replace the constructor's omitted-argument behavior with `false`, and verify
that lowering still supplies `true`. Existing schema-v2 tests independently
round-trip both booleans for all eight shapes, optimizer tests cover legal
`false`, and backend tests demonstrate that `false` removes the runtime helper.

Machine-readable evidence, including the 116 file paths and per-kind counts,
is generated by `scripts/audit_bounds_checked_provenance.py` in
`bounds_checked_provenance_qualification.json`. Both historical blocked
RUST-3.1 artifacts are preserved without modification.
